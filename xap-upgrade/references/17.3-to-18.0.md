# XAP Upgrade: 17.3 → 18.0

> Verified against releases **17.3.0** and **18.0.0** specifically (the installs available), by
> comparing jar versions, class-file versions and the distribution layout. The grid behavior
> notes were confirmed on a live 18.0.0 grid while the training labs were being upgraded. Named
> at the 17.3 → 18.0 level to match how GigaSpaces' own documentation is organized. See
> `references/dependency-compatibility-checklist.md` for what these numbers mean and why they
> matter.

18.0 has two breaking changes: **Java 25 is required**, and **the V2 REST Manager API and
ops-ui on port 8090 are retired**. Plan for both before anything else.

| Component | 17.3 | 18.0 |
|---|---|---|
| Java | 17, 21 | **25 only.** The XAP jars are Java 25 bytecode (class-file major 69, was 61) |
| Spring Framework | 7.0.8 | 7.0.9 (patch only) |
| Spring Security | 7.1.0 | 7.1.1 (patch only) |
| Spring Boot Loader | 4.1.0 | 4.1.1 (patch only) |
| Jetty | 12.0.34 | 12.0.38 |
| Hibernate | *(project-supplied; not bundled by XAP)* | not separately confirmed for 18.0.0. 7.1.0.Final was confirmed working with the Mirror on 18.0.1 (Spring 7.0.10); see `18.0-to-18.0.1.md` |
| Manager REST API | V2 on 8090 (deprecated since 17.2) + V3 on 9090 | **V3 only, on 9090** |
| Default lookup group | `xap-17.3.0` | `xap-18.0.0` |

---

## Breaking change 1: Java 25

**Everything that loads XAP jars must run on JDK 25**: the grid itself, every client
application, every Processing Unit, and the `gs.sh` CLI. On JDK 17 or 21 they fail at class
loading with `UnsupportedClassVersionError`, e.g. "class file version 69.0 … this version of the
Java Runtime only recognizes class file versions up to 61.0". JDK 17 and 21 support is dropped
outright. There is no transition release in which both work.

What to change:

- **Build:** set `maven.compiler.source`/`target` (or `release`) to `25` in every `pom.xml`, and
  use a Maven Compiler Plugin that handles Java 25 (`3.13.0` is confirmed working). See
  `gigaspaces-xap`'s `maven-pom.md`.
- **IDE run configurations:** point them at a JDK 25 runtime. A run configuration that pins an
  alternative JRE of 17 fails even after the pom is fixed.
- **Container images:** move base images to a Java 25 runtime (e.g. `eclipse-temurin:25-jre`).
- **Grid hosts:** install JDK 25 and make it the one GigaSpaces uses. Set `JAVA_HOME` in
  `bin/setenv-overrides.sh`, which every `gs.sh` and agent command reads. Setting it only in
  `service-overrides.sh` covers agent-spawned services but not the CLI you type, which then falls
  back to the system Java and fails with the class-file error above. *(Confirmed on 18.0.1.)*
- **Scripts:** any helper script that runs a bare `java` against XAP jars picks up the system
  default. Use `$JAVA_HOME/bin/java`.
- **Your own dependencies:** check that every third-party library the application uses runs on
  Java 25. This is checklist #1; libraries that use reflection into JDK internals are the usual
  problem. One example seen in practice: a JShell-based Jupyter kernel needed
  `JDK_JAVA_OPTIONS=--add-opens=java.base/java.lang=ALL-UNNAMED` to load a space proxy on
  Java 25.

## Breaking change 2: V2 REST Manager and ops-ui (port 8090) retired

The V2 manager REST API and the ops-ui built on it were deprecated in 17.2 (see
`17.1-to-17.2.md`). **In 18.0 they are gone.** The manager no longer serves the V2 API or ops-ui
on 8090. The REST API is now **REST API V3 only, on port 9090**, together with **SpaceDeck**, the
web UI that replaces ops-ui.

- **Start it explicitly or with `--auto`:** REST V3 comes from the `--restv3` agent option and
  SpaceDeck from `--webui`. In 18.0, `gs.sh host run-agent --auto` includes both
  (`--manager --webui --restv3`). A startup script that names its services one by one, e.g.
  `run-agent --manager --gsc=2`, gets **no REST API at all**. Add `--restv3 --webui`.
- **URLs change in host, port and path:** `http://<host>:8090/v2/...` becomes
  `http://<host>:9090/api/v3/...`. Swagger UI is at `/api/v3/swagger-ui/index.html`, and the
  OpenAPI document is served next to it.
- **Endpoints are not one-to-one.** V3 is a different API, not V2 under a new prefix: paths,
  request bodies and parameter names differ. Re-write each V2 call against
  the V3 OpenAPI document. Don't transform the URLs mechanically.
- **Clients built on V2 have no server:** scripts calling `:8090/v2`, monitoring checks, CI
  deploy steps, the `xap-admin-rest-java-client-v2` Java client, and custom REST Manager plugins
  written for V2. Plugins have to be rebuilt against REST V3.
- **Kubernetes:** the 18.0.0 manager Helm chart exposes only 9090 (REST V3 / SpaceDeck). Update
  NodePort/Ingress definitions and any `kubectl port-forward ... 8090:8090` instructions.
- **Security:** on a secured grid, REST V3 uses HTTP basic authentication against the grid's
  security configuration. The V2-era manager option `-Dcom.gs.manager.rest.ssl.enabled` is not
  needed for REST V3. *(Confirmed on 18.0.1.)*
- The 18.0.0 distribution still contains `lib/optional/rest/xap-rest.war` (the V2 web app). It is
  not served, and it is removed from the distribution in 18.0.1. Don't plan to keep using it.

GigaSpaces also retired the legacy web UI on port 8099 in 18.0. SpaceDeck on 9090 replaces both
it and ops-ui. The Swing-based `gs-ui` desktop client still ships as a legacy tool.

## Smaller items

- **Default lookup group** is version-derived: `xap-18.0.0`. A client that relies on the default
  group, rather than setting `GS_LOOKUP_GROUPS` or locators explicitly, won't find a grid on a
  different version. Set groups and locators explicitly on both sides.
- **Client/server alignment** (checklist #4): a client that moves to the 18.0 jars has to move to
  JDK 25 at the same time, so plan each client's JDK move together with its XAP version move.
  Whether a 17.x client can keep talking to an 18.0 grid during the transition is the "client
  older than server" case: ask GigaSpaces support.
